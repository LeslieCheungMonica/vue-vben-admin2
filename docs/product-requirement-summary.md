# 敏感信息检测与代码风险扫描平台 — 需求总结与产品个人经验

> 本文档基于项目实际代码与业务文档整理，用于沉淀需求分析思路与个人产品经验。

---

## 一、产品概述

### 1.1 产品定位

本产品是一套面向政企 / 运营商体系的 **敏感信息泄露检测与代码风险评估平台**，核心解决"数据通过 API 流动时，敏感信息是否被合规地处理"这一问题。产品包含三大能力域：

| 能力域 | 模块 | 定位 |
|--------|------|------|
| **敏感信息检测** | 总览、检测结果、日志数据、模型配置、知识库、LLM 配置、智能助手、评估报告 | 从日志 / 流量中识别身份证、手机号、银行卡、姓名、地址、邮箱、IP、密码等敏感数据，评估接口风险 |
| **代码任务扫描（Cosmic）** | 资源上传、任务管理、任务详情证据树、报告导出 | 结合 COSMIC 元数据，把代码资产与业务功能映射，逐接口定位敏感数据暴露点并产出证据 |
| **业务测绘（WAPE）** | 业务系统创建、WebServer 启动、API Endpoint 任务 | 对存量系统做业务与 API 接口的自动态测绘，为后续检测提供扫描对象清单 |

### 1.2 技术栈

- **前端**：Vue 3 + Vite + Ant Design Vue + ECharts，基于 Vben Admin 5.x 二次开发（monorepo，支持 web-antd 等多套壳）
- **后端**：Java（`com.asiainfo.crm.security`，敏感检测服务）+ Python 扫描服务（Cosmic / WAPE，负责代码静态分析与任务调度）
- **检测引擎**：规则模型（正则）+ 大语言模型（LLM）双通道；知识库提供 RAG 上下文增强
- **对接框架**：OpenCode / Agent，用于业务测绘与代码分析型任务

### 1.3 核心价值

1. **能看见**：把散落在日志中的敏感数据变成可视化的风险分布（总览大盘、风险等级、敏感类型分布、Top 高危接口）。
2. **能定位**：从"检测结果"反查到 traceId 对应的接口、操作、请求 / 响应报文，做到可回溯。
3. **能复检**：规则检出后可用 LLM 二次复核，降低误报；支持全量复检与按接口路径复检。
4. **能治理**：提供模型配置、知识库沉淀、评估报告与整改建议，形成"发现 — 复检 — 评估 — 整改"闭环。

## 二、需求总结

### 2.1 业务背景与痛点

- **合规压力**：行业监管要求对个人敏感信息"最小化采集、脱敏展示、可追溯"，企业需要证明自身 API 没有把敏感信息明文返回。
- **存量系统复杂**：大量老系统无统一网关、无统一日志规范，敏感数据"随业务接口随手返回"，问题隐蔽。
- **人工审计成本高**：人工翻阅接口日志 / 代码定位敏感字段，效率低、覆盖不全、结论不可复用。
- **规则引擎误报率高**：纯正则识别身份证、姓名等类型误报多；LLM 能理解上下文但成本高、不稳定，二者需结合。

### 2.2 目标用户与角色

| 角色 | 诉求 |
|------|------|
| **安全合规负责人** | 一屏看到全局风险水位、能一键出评估报告，向上汇报 |
| **安全检测工程师** | 配置检测模型、调规则、跑批量复检、核实高危接口 |
| **研发 / 接口负责人** | 定位自己负责接口的敏感字段暴露情况，获取证据与整改建议 |
| **架构 / 运维** | 通过日志数据与 traceId 做链路回溯、确认脱敏策略 |

### 2.3 核心功能需求

#### 需求一：检测结果总览（Dashboard）

- 顶部统计卡：总日志数、检测发现数、高危接口数、风险接口数。
- 风险等级分布饼图、敏感类型分布柱状图。
- 高危接口 Top5 列表，一键跳转检测结果明细。
- 经验点：**指标的定义要先定清楚**（"高危接口数"= CRITICAL+HIGH 的接口聚合数，"风险接口数"= 有敏感检出的接口数），避免口径在汇报时被挑战。

#### 需求二：日志数据管理

- 日志列表 + 详情（请求 / 响应头、体、耗时、traceId、操作员），支持按时间、接口路径、操作员、检测状态筛选。
- 支持"新增日志并检测""对单条日志检测"（长超时 120s，服务端同步检测）。
- 经验点：日志是"素材"，检测是"加工"，**先建素材再谈加工**，否则演示无真实数据可用。

#### 需求三：检测结果管理

- 检测结果列表：按风险等级、敏感类型、操作员、时间范围多条件筛选 + 分页。
- 详情：traceId、接口路径、敏感类型、风险等级、确认状态（未确认 / 已确认 / 已忽略）、敏感信息明细表（类型 / 字段 / 脱敏值 / 来源）。
- 经验点：**"脱敏值"是必须字段**——安全管理产品自己不能泄露敏感数据，列表与详情一律展示脱敏后的值，这是合规底线。

#### 需求四：LLM 批量复检

- 复检范围二选一：全量日志 / 指定接口路径关键字。
- 结果统计：检测总数、检出敏感、安全、LLM 成功 / LLM 失败。
- 明细：每条 traceId 的规则命中、LLM 判定、敏感类型；长超时（300s）。
- 经验点：**给 LLM 失败留出口**。LLM 不稳定，统计里单独展示"LLM失败"数量而不是整体报错，既诚实又给用户降级预期。

#### 需求五：检测模型配置

- 模型类型：规则模型（正则 pattern）与 LLM 模型两类。
- 模型属性：敏感类型、优先级（1-10 滑杆）、置信度、启用开关、描述。
- 支持在线"模型测试"：输入样本文本，返回是否检出、置信度、匹配结果。
- 经验点：**规则模型一定要可视化测试**。正则规则可读性差，不给测试入口，配置人员完全没法用；测试面板是规则类产品的"必配功能"。

#### 需求六：知识库（RAG 增强）

- 知识条目管理：列表、详情、新增（标题 / 内容 / 分类 / 标签 / 来源）。
- 语义搜索；AI 知识增强（对查询做知识补全，超时 120s）。
- 经验点：知识库把"检测经验"从个人脑子沉淀成组织资产，**是 LLM 类检测产品区别于纯规则产品的分水岭**；但内容治理要跟上，否则脏知识会拉低检出质量。

#### 需求七：LLM 配置与连接管理

- 配置 provider、模型名、apiUrl、apiKey、temperature、maxTokens。
- 提供"测试连接"。
- 经验点：**apiKey 走服务端保存与校验，前端只读**；连接测试是接入类功能的第一个验收标准，先让用户 30 秒内看到"通了"。

#### 需求八：智能助手（Agent 对话）

- 同步聊天（非流式回退）：支持 thinking / analysis / data / structured_data / answer 多步骤响应。
- 结构化风险数据展示：风险等级定义、风险接口列表、统计、敏感类型分布，按 overview / risk_only / type_dist / suggestion 多种展示模式。
- 经验点：**把 Agent 的中间思考步骤展示出来**（thinking → 分析 → 取数），让用户信任结论；结构化卡片比纯文字回答更有"产品感"。

#### 需求九：评估报告

- 一键生成评估报告：概要统计、风险等级占比、敏感类型分布、Top 高危接口、整改建议列表。
- 支持时间范围、是否包含明细选项。
- 经验点：**报告是安全产品的交付物**，管理者不看系统只看报告；"整改建议"字段是加分项，把系统从"发现问题"推进到"给出办法"。

#### 需求十：代码任务扫描（Cosmic）

- 资源管理：上传代码资源、上传 COSMIC 元数据 Excel，可删除。
- 任务管理：创建（绑定代码资源 + COSMIC 资源 + 列映射）、启动 / 停止 / 删除、状态流转（wait-to-start → running → completed）。
- 任务详情：树形证据结构，每个输入项给出前端 / 后端证据（搜索关键字、路径、代码片段、行号）、业务上下文、置信度、整改建议。
- 导出 Excel 报告。
- 经验点：**"证据"是这个模块的灵魂**。纯扫描不给证据，用户无法判断结论对错；证据树（字段级定位到文件、行号、代码片段）+ 置信度，是把工具变成"可信产品"的关键。

#### 需求十一：业务测绘（WAPE / API Endpoint）

- 按 system_name 去重创建业务测绘记录，关联资源路径。
- 启动 WebServer（拼装代码路径 → 调用 OpenCode start_server）。
- API Endpoint 任务：创建 / 列表 / 启动 / 停止 / 详情，动态测绘系统接口。
- 经验点：**先测绘后检测**的思路很正确——不知道系统有哪些接口，扫描就是无的放矢；把"发现接口"做成独立能力，反哺检测引擎的覆盖面。

### 2.4 非功能需求

| 类别 | 要求 | 落地体现 |
|------|------|----------|
| **性能** | 大日志量下批量复检不能同步卡死 | batchRecheck 超时 300s、detect 类接口 120s；批量结果带回进度口径 |
| **安全合规** | 敏感数据不能明文出现在前端 | 列表 / 详情一律展示脱敏值；apiKey 服务端管理 |
| **可用性** | LLM 不稳定时系统仍可用 | 规则 + LLM 双通道，LLM 失败单独统计；Agent 支持流式与非流式回退 |
| **可扩展** | 检测能力可配置、可持续累积 | 模型优先级 / 启用开关 / 置信度；知识库持续沉淀；模块化 API 前缀 |
| **可追踪** | 每个检测结果可回溯 | 全链路 traceId 贯穿日志、检测结果、复检明细 |

## 三、产品个人经验

### 3.1 需求分析：先问"谁在看、看完做什么"

1. **按角色拆诉求，而不是按页面拆功能。** 本产品最大的需求分层来自三个角色：管理者要"结论"（报告、大盘）、工程师要"能力"（模型、复检、知识库）、研发要"证据"（详情、代码定位）。把每个需求挂到角色上，优先级立刻清晰。
2. **指标口径先于界面。** 总览页的"高危接口数""风险接口数"在开发前就该和业务方对齐口径（是接口数还是检出数？含不含已忽略？）。口径不清是需求评审最大的坑，回头改报表最伤团队信任。
3. **从"证据链"反推数据模型。** 这个产品能成立，是因为每一条结论（检出敏感）都能被 traceId 一路追溯到报文和代码。做需求时先画证据链（结论 → 明细 → 报文 → 代码），数据模型自然就出来了。
4. **边界场景要写进需求。** "LLM 失败怎么办""复检没有数据怎么办""正则写错怎么办"这些边界，比主流程更能决定产品口碑。需求文档里没有边界条款，上线就会被用户用边界问题打脸。

### 3.2 产品设计：让安全产品"可解释、可演示"

5. **可视化是安全的刚需。** 安全数据量大且抽象，饼图 / 柱状图 / TopN 列表能把"风险水位"讲给不懂技术的人听。ECharts 的分布图是汇报演示的标配。
6. **脱敏展示就是产品价值观。** 一个检测敏感数据的产品，自己的页面上绝不允许出现明文敏感值。这是设计底线，不是功能选项；演示时它反而是最强的信任背书。
7. **长任务要有"过程感"。** 批量复检 300s，如果没有进度 / 结果分段展示，用户会以为系统卡死。把"进行中 → 部分结果 → 失败计数"都表达出来，体验差异极大。
8. **智能能力要"半透明"。** Agent 展示 thinking / analysis / data / answer 的分步过程、LLM 判定给出命中明细，用户才会信任"AI 说这是敏感信息"。黑盒 AI 在安全场景不受欢迎。
9. **报告即交付物。** 管理者不看系统，只看报告。把报告做得完整（概览 + 分布 + Top 接口 + 整改建议），产品就赢了一半。

### 3.3 技术落地：从 demo 到可用产品

10. **规则 + LLM 双通道是最务实的架构。** 纯规则快但误报高，纯 LLM 准但贵且不稳。先用规则兜底覆盖、再用 LLM 复核精调，成本与准确率平衡得最好。
11. **配置化是产品的护城河。** 模型（规则 / LLM）可配置、优先级 / 置信度 / 开关可调、知识库可沉淀——这些把"写死检测逻辑"变成了"运营检测能力"，产品才具备面向不同客户的复制能力。
12. **证据结构化是可信的基础。** Cosmic 模块把结论落到"文件 + 行号 + 代码片段 + 置信度 + 建议"，这是被工程师用户接受的唯一方式。结构化证据（evidence 树）比结论列表高一整个段位。
13. **同步/异步和超时策略要按接口性质定。** 单条检测 120s、批量复检 300s、报告生成 60s、知识增强 120s——长耗时接口统一给足超时并做进度反馈，前端别用默认 10s 超时去坑用户。
14. **先建素材（日志）、再谈加工（检测）。** 演示 / 联调阶段最缺的是真实日志数据，`addAndDetect` 这类"喂数据"接口是 demo 的生命线，早期就要有。

### 3.4 踩过的坑与反思

15. **坑：口径不一致导致统计数字互相打架。** 总览、报告、检测列表三处"风险"定义曾不一致。反思：任何统计口径变更都要过一遍所有展示点，最好收敛成统一的数据服务（如 statistics 聚合接口）。
16. **坑：LLM 结果直接当结论，无失败兜底。** 早期 LLM 一挂整个复检流程就报错。反思：把"LLM 失败"建模成一种正常状态，主流程永远可完成，失败单独计数并提示重试。
17. **坑：敏感类型枚举散落各处。** ID_CARD / PHONE 等枚举在前端 mapping、下拉、后端字典里各自维护，极易漂移。反思：枚举映射应收敛到单一来源（`utils/mapping.ts` + 后端字典），新增类型一处改、处处生效。
18. **坑：规则配置不给测试入口。** 正则规则上线后没人敢动，因为改了不知道会不会误伤。反思：配置型能力必须配套"测试/试运行"闭环，否则配置功能形同虚设。
19. **坑：扫描不给证据，结论被质疑。** 早期 Cosmic 只给"疑似/不疑似"，被研发用户反复挑战。反思：任何判断类结论都必须携带可核验的证据链和置信度。

### 3.5 团队协作与流程建议

20. **需求评审用"用户故事 + 验收标准"而不是功能清单。** 例如"作为安全工程师，我希望批量复检能按接口路径圈定范围，以便聚焦高危接口"，比"做批量复检按钮"清晰得多。
21. **demo 先行、口径先行。** 一个能跑通全链路的演示（日志 → 检测 → 复检 → 报告）比任何 PPT 都能凝聚需求共识；先把纵向链路打通，再横向铺模块。
22. **沉淀接口文档与业务文档。** 本仓库的 `docs/`（api.md、cosmic_api.md、biz_survey.md、api_endpoint.md）让前后端、扫描服务多方协作有据可依；文档要跟着代码更新，否则文档漂移比没有文档更伤。

## 四、一句话总结

> 做安全类产品，本质是**把"看不见的风险"变成"看得见的证据"，再变成"能行动的整改"**。
> 需求上：围绕角色分层（管理者要结论、工程师要能力、研发要证据）；
> 设计上：坚持可解释（脱敏、证据、分步思考）、可演示（大盘、报告）、可运营（模型 / 知识库可配置）；
> 落地上：规则 + LLM 双通道、配置化护城河、证据结构化、口径统一。
> 这条主线贯穿了从需求到产品的每一步。
